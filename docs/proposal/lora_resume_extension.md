# LoRA 恢复与加训方案

状态：已按 UI → 独立界面验收 → 后端 → 实际训练 → 前后端联调的顺序实施，2026-09-10。基于 `d85aeb1d`，工作分支 `codex/lora-training-continuation`。只在预设后新增同风格任务下拉栏，其他布局、按钮名称及历史页保持现状。

## 1. 目标与当前问题

用户从训练配置页明确选择原训练，把总轮次由 30 改为 40，恢复已保存的训练状态后只训练剩余部分。任务记录、已有输出和 V100 环境得到保留。

当前配置页顶部只有“训练”和“测试”。源码中的“继续训练”位于检测到 checkpoint 后才显示的弹窗，不是常驻入口。该弹窗的 `resumeTrain()` 仍调用新任务提交逻辑，没有绑定来源任务或显式状态；daemon 新任务的归属校验会跳过其他任务的状态。历史任务的恢复接口又只接受停止/失败任务，复用原目标，不能给已完成任务增加轮次。

相关代码：

- `webui/frontend/src/views/ConfigEditor.vue`：工具栏、训练启动、checkpoint 弹窗。
- `webui/api/tasks.py`、`webui/services/task_service.py`：任务恢复接口。
- `scripts/daemon/manager.py`：状态发现、逻辑任务归属、恢复预约与提交。
- `library/training/checkpoints.py`：状态完整性、归属及签名校验。
- `train.py`：总轮次/步数解析、恢复游标、配置签名。
- `library/training/schedulers.py`：比例预热依赖训练总步数。

本地只读检查发现 `output/ckpt` 中有 10 份 schema v3 的 `train_state.json`，均带任务归属信息。发现 sidecar 不等于通过完整状态验收，不能直接标为可继续。

## 2. 页面入口与交互

只在“预设”后、现有操作按钮前增加“训练任务”下拉栏，使用相同的 outlined、compact、高度、背景、边框和展开图标，支持清空。现有预设的新建/删除操作仍归预设控件所有。“训练”和“测试”按钮的文案、样式及位置顺序保持不变，不增加继续训练按钮或对话框，不重命名参数组，不改造历史页或监控页。

```text
训练方法 [lora]  变体 [LoRA]  预设 [V100]  训练任务 [留空为新建 ▼]
                                          [保存] [刷新] [训练] [测试]
```

以上换行只为文档排版。宽屏仍保持一行，由现有工具栏栅格调整选择框宽度容纳新控件；窄屏沿用现有换行规则。

下拉值绑定逻辑任务 id 和其最新 attempt，不绑定名称。选项按最近时间排列，展示任务名、日期、状态及保存进度，例如“示例 LoRA · 09-04 · 已完成 30 轮”。重名时补充短任务 id。列表只列当前训练方法/变体对应的任务；预设名称不作为恢复兼容性的依据。不可继续的记录显示为禁用项，在该项说明具体原因，无需新建状态面板。

流程：

1. **留空**：原表单仍是当前变体/预设的新训练配置，点击原“训练”按钮创建新逻辑任务。禁止仅凭同名文件自动续训。
2. **选中任务**：读取原任务不可变快照并回填现有参数表单。后台检查最新 attempt、状态完整性、模型与数据；验证完成前阻止提交。首版使用原表单的只读能力保护除训练预算外的参数，布局、字段名称及参数组不变。选中任务后，执行参数以原任务快照为准；预设控件显示原任务的预设名称，缺失的旧预设仅作为快照来源展示，不重新套用当前同名预设。
3. **恢复中断**：已有进度低于原目标，保持现有“最大轮次”值直接点“训练”，从状态继续完成原目标；调大该值则恢复后训练到新目标。
4. **完成后加训**：例如原来完成 30 轮，将现有“最大轮次”改为 40，再点同一个“训练”按钮；后端判定为加训，接着训练剩余 10 轮。未调大时使用现有字段错误/通知机制提示“已达到 30 轮，请提高最大轮次”。不自动选择目标，不新开模式选择或启动确认弹窗。
5. **启动**：原按钮触发后台 prepare 与 submit，沿用现有加载、错误通知和监控跳转。新 attempt 归原逻辑任务，现有监控页读取新的累计目标，无需增加新 UI。
6. **清空或切换**：清空任务恢复之前的新建配置草稿。主动切换训练方法、变体或预设时先退出任务模式，再加载对应的新建配置，避免把新预设偷偷用于旧状态；程序性回填原任务预设不能触发此清空逻辑。切换任务时隔离各自预算草稿，不能串用来源或目标。

沿用现有“最大轮次”字段，它始终表示总轮次，不新增“再训练几轮”输入。epoch 中途中断时，下拉选项显示“第 N 轮中断，step S”，按真实 step/批次游标计算恢复位置，不能把 `current_epoch=N` 当作已完成 N 轮。

历史页保持现有 UI 和恢复按钮；其后端接口可以复用共享恢复逻辑，仍按原目标恢复。任务下拉失效或候选刷新失败时保留选中任务并禁止启动，不能自动清空导致下一次点击变成新建训练。页面重新打开默认留空，不自动恢复来源任务选择。

## 3. 参数与模式边界

| 场景 | 配置来源 | 恢复内容 | 任务关系 |
| --- | --- | --- | --- |
| 新建训练 | 当前表单 | 新初始化 | 新逻辑任务 |
| 恢复中断 | 原任务快照 | 权重、优化器、调度器、随机状态、步数与数据游标 | 同一逻辑任务的新 attempt |
| 完成后加训 | 原任务快照，仅改变目标预算及必要的输出定位 | 同上 | 同一逻辑任务的新 attempt |
| 基于权重新训练 | 当前表单及明确选择的 LoRA 权重 | 仅权重；步数、优化器重新开始 | 新逻辑任务，记录来源 |

选中任务时，现有参数表单展示原任务快照，首版仅允许调整训练预算。新建模式的未保存草稿单独保留，不自动保存或应用到原任务。若要修改数据、rank、模型、优化器或学习率，应清空任务，利用现有权重字段建立独立训练；完整状态恢复不混入这些变更。

原“保存”按钮在任务模式中只保存该任务最新 attempt 对应的预算草稿，可使用独立的本地草稿键；通过现有通知说明保存结果，不写入原任务快照、全局预设或变体文件。“训练”直接读取当前预算，无需先点保存。“刷新”重新读取所选任务及其快照，不走新建配置的重载分支。原“测试”流程保持现状，不因选中任务而启动恢复训练。

只有 `.safetensors`、没有完整训练状态时，在下拉项说明“缺少完整训练状态”，禁用选择。用户仍可留空任务并在原有“续训与热启动”参数组填写权重路径，不增加新的热启动入口。绝不静默降级到权重热启动或从头训练。

显式 `max_train_steps` 优先的旧任务沿用现有最大步数字段，只允许编辑有效的步数预算，轮次字段保持只读。如果该字段未能由现有表单呈现，则将该类任务标为首版暂不支持，不新增面板。普通 epoch 任务以总轮次为权威输入，由后端按照原数据与累计规则换算目标步数。

“续训与热启动”及其他参数组名称、布局保持不变。

## 4. 后端提交协议

已实现以下 WebUI 接口：

- `GET /api/tasks/continuation-candidates?variant=lora`：列出来源、能力与不可用原因。
- `GET /api/tasks/{task_id}/continuation`：读取原快照字段及可用状态，仅有效预算字段可编辑。
- `POST /api/tasks/{task_id}/continuation/prepare`：接收来源 attempt、预算类型和值，推导 `mode=resume|extend`，返回有效目标步数、恢复步数及 10 分钟有效 token。准备记录在 daemon 中绑定来源、配置、状态、原调度预算及目标。原“训练”按钮在后台调用，无新增弹窗。
- `POST /api/tasks/{task_id}/continuation`：接收 token 和幂等键；后端重新检查并提交。

服务端决定来源状态路径、逻辑任务归属和输出路径，不信任前端传入的任意 `root_job_id`、状态路径或配置覆盖字典。WebUI 和 daemon 使用同一套候选与验证逻辑；真正的最终校验和原子提交在 daemon 内完成。

提交要求：

1. 来源必须是该 root 的最新 attempt，且整个 root 没有运行中、排队中或正在预约的 attempt。
2. schema v3 所有权、publication marker、必需 payload、配置/数据/模型签名全部满足。
3. prepare 绑定来源 attempt、状态 generation/manifest、配置摘要及目标；提交与真正加载时再验证。状态发生变化返回可解释的冲突，不替换为其他状态。
4. 增加轮次的新目标必须大于原目标及恢复 step；普通恢复保持旧目标。不能只为复用旧恢复筛选器而先篡改旧任务的目标。
5. 在现有 root reservation 下创建 child attempt：保持 `root_job_id`，`parent_job_id` 指向来源，递增 `attempt_index`，记录 `continuation_kind`、旧/新预算及来源状态。
6. 从旧快照复制出新 attempt 的不可变快照，应用经过白名单验证的预算变化，显式注入 `--resume`。同步更新新 attempt 的 `target_steps/target_epochs`。旧 job 与旧快照保持不变。
7. 元数据、快照和恢复引用完整写入后再入队，幂等重试返回同一个 attempt。双击不能创建两次加训。

已有 continuation attempt 的旧 `/resume` 入口转调共享逻辑，保持目标不变；普通历史任务原恢复入口保留既有行为。保留任务所有权校验；不能为方便加训删除校验或修改旧状态的 owner。

新建训练必须显式使用 fresh 初始化策略，禁止按同名目录自动拾取状态，并预先检查输出重名。该策略只由启动层控制，不混入数值配置签名。根据任务下拉是否为空选择明确的提交路径，不再触发旧 checkpoint 弹窗中的“继续/清理并训练”分支；同名冲突使用现有错误通知提示修改输出名称，不能自动清理旧状态。

## 5. 学习率、输出与旧记录

### 学习率

加轮次不仅改变停止条件。当前比例预热用 `lr_warmup_steps * max_train_steps` 计算，直接按新目标重新构建会改变预热长度；部分衰减调度也依赖总步数。

首版保证普通 LoRA 的 `constant`、`constant_with_warmup`：保存或从可信原快照解析原始有效预热步数，恢复调度器进度后沿用原值，不重新预热。实际学习率沿用原有训练日志，不增加信息面板。旧快照无法可靠确定调度上下文时阻止加训并通过现有错误机制解释原因。

对依赖训练总长度的 cosine/linear 等调度器，普通“原目标恢复”继续支持；“增加目标”在完成逐种数值验收前明确显示不支持。后续可增加独立的加训阶段调度策略，不能静默把已经结束的调度曲线拉长。首版也不扩展 T-LoRA 动态 rank、分阶段分辨率和多卡训练。

调度上下文作为显式 continuation 元数据持久化，参与准备与加载验证。配置签名的兼容处理只允许预算和受控输出定位等明确差异，不能为了通过签名检查忽略所有新增字段或配置变化。

### 输出

原最终模型及完整来源 state 保留为只读历史。每次加训把新模型和状态写入独立的 continuation 子目录，在原逻辑任务中展示并维护最新有效产物引用。不能直接覆盖原最终模型或来源状态，再指望失败后回滚。

落地时需要把“训练语义配置”与“本次输出物理位置”分开：使用受控的 attempt 输出路由，避免仅改 `output_dir` 导致签名不兼容。扩展 `output_layout` 和候选发现，让后续中断恢复能找到最新 attempt 的状态。所有参数快照仍记录实际输出路径，且模型列表、推理和导出读取新产物引用。

### 旧记录

首版优先支持所有权完整、配置快照和二进制状态可校验的 schema v3 记录。不能凭输出同名、日期接近或当前 GUI 配置去补写历史归属。

缺少 owner/快照或旧 schema 的记录在下拉项展示原因；权重热启动使用现有配置字段。完整 legacy state 导入作为后续功能，需有独立的来源选择与验证流程，不在本轮增加入口；不把批量改写历史 `train_state.json` 作为更新动作。

## 6. 实施顺序与验收

1. **UI 落地**：仅增加预设后的任务下拉，完成快照回填与独立草稿、清空/切换行为；原“训练”按钮按选择分流。
2. **UI 独立验收**：通过受控接口桩验证控件风格、布局、原目标阻止、目标草稿、清空恢复及提交契约。
3. **后端落地及验证**：候选发现、完整状态校验、prepare/submit、原子提交、输出隔离、预算和调度上下文；单元测试及隔离 V100 实际训练。
4. **前后端联调**：真实浏览器操作真实 WebUI/daemon，验证连续加训与中断恢复；复核本地服务、原资产和环境后交付。

必须覆盖的验收案例：

- 已完成 30 轮 → 目标 40 轮，恢复 global step 和优化器状态，只执行剩余预算。
- 第 N 轮中途停止 → 恢复到正确批次，不把进入某轮当作完成某轮。
- 历史页恢复不改变目标；加训确实使用新 attempt 的目标。
- 连续加训 30 → 40 → 50 使用最新来源状态，累计曲线与产物对应正确。
- 比例预热不随新增轮次重算，恢复前后学习率及参数更新与参考过程符合规定。
- 缺状态、损坏 payload、错误 owner、数据或模型不匹配时，阻止启动并显示原因；没有自动从头训练回退。
- 准备后状态变化、重复提交、队列已有同 root 任务时不产生重复 attempt。
- 新建训练绝不因同名文件自动续训，也不覆盖已有模型。
- 任务留空时新建，选中后沿用快照；修改现有最大轮次即可加训，没有第二个轮次输入或新的启动弹窗。
- 清空任务能恢复新建草稿；选择不同任务不会串用配置或预算；保存续训草稿不修改原任务/全局配置。
- 用户切换预设退出任务模式；任务快照回填预设不会错误清空任务；来源失效不会静默变成新建。
- 未保存表单、窄屏换行、不可用下拉选项、异步加载和启动失败的原有反馈机制均可实际操作。
- V100 保留 Torch 2.10.0+cu129 / torchvision 0.25.0+cu129 / Triton 3.6.0；使用原任务精度与注意力配置，不安装依赖、不切换 FlashAttention。
- 完成标准为任务成功且预期权重/状态产物有效；测试出图不是必需步骤。

本轮只交付方案；实现时需要补充对应契约测试，涉及数值语义的调度处理按仓库 Tier 1.5 要求提供小型 bench 与不变量测试。


## 8. 实现与验收补充

- 配置页使用 `useTrainingContinuation` 隔离新建草稿和每个来源 attempt 的目标草稿；清空任务恢复新建表单，保存只写本地续训草稿。选中后锁定方法、变体、预设及非预算字段。
- daemon 将完整来源状态 reflink/copy 到新 attempt 的私有 `resume-input`，全量校验后提交。新产物位于原模型目录的 `continuations/<attempt>/` 下，递归模型发现沿用现有实现。
- 首次配置快照写入之前就切换物理输出目录。原输出、原状态和源任务快照均不覆盖。新建模式在提交及训练器首次写入前都检查输出冲突。
- 每次新训练记录实际数据 blueprint；后续续训从该记录加载。历史任务若没有 blueprint 留档，仍通过原配置/数据签名严格验证；数据或旧配置与当前运行时不兼容时会拒绝启动，不能保证任意旧版本任务可恢复。
- 普通 LoRA、单进程完整状态是当前支持边界。增加目标仅支持 `constant`、`constant_with_warmup`，自定义调度器不支持；原目标恢复保留原调度 horizon。
- 没有最新 attempt 的完整状态时显示不可用，不自动回退到更早 attempt。旧任务缺少签名、必需二进制状态、完成标志或源模型/数据文件时同样阻止。
- 独立 UI 使用只读代理加提交桩验证；实际联调使用 18081 WebUI → 18765 隔离 daemon → V100 训练器。没有使用用户正式 LoRA 任务执行验收加训。
- 数值基准：`bench/continuation/run_bench.py`；验收证据与已知测试限制：`output/validation/continuation/REPORT.md`。
